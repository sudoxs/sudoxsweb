# ZRAM: 圧縮RAMスワップ

ZRAMはRAM上に圧縮スワップデバイスを作成します。書き込まれたページはその場で圧縮されるため、CPUサイクルと引き換えに実効メモリ容量を増やせます。Fedora、Pop!_OS、そしてほとんどのAndroidデバイスでは、ZRAMがデフォルトのスワップバックエンドです。

**なぜ重要か:** CPUに余裕があるのにRAMがボトルネックになっている場合 — 似たプロセスが多いワークロード（Electronアプリ、Chromiumのタブ、同じイメージを動かすDockerコンテナ）、大規模ビルド、VM、仮想ネットワークラボ — ZRAMは実使用でメモリを2倍から10倍以上に増やせます。同一メモリページを多く共有するワークロードでは4:1〜10:1の圧縮率が一般的で、冗長性の高いコンテナワークロードでは20x〜30xも観測されています。

**トレードオフ:** 圧縮・展開にはCPU時間とレイテンシがかかります。デスクトップ用途ではZRAMを調整すればディスクスワップはほぼ使われなくなり、SSDにとって有利です。ただしZRAMサイズを闇雲に大きくするのは危険です — 48GBマシンに128GBのZRAMは、特定のラボケースで動いたとしても一般用途では無謀です。

## セットアップ

モジュールをロードし、永続化設定を行います。

```bash
# zramモジュールをロード
sudo modprobe zram

# ロード確認
lsmod | grep zram
```

ZRAMデバイスの数とサイズを設定します。ユーザー空間ツールは `zramctl` です。

```bash
# zramデバイスを作成（既存のものでも可）
sudo zramctl --find --size 32G --algorithm zstd
```

- `--find` — 最初の空き `/dev/zramN` を選択
- `--size` — 非圧縮時の容量（これが圧縮される）
- `--algorithm` — `zstd` が圧縮率と速度のバランス最良。`lz4` は速いが圧縮率は低い

スワップとしてフォーマットし有効化します。

```bash
# スワップとしてフォーマット
sudo mkswap /dev/zram0

# 優先度を高くして有効化（カーネルがディスクスワップより優先する）
sudo swapon --priority 100 /dev/zram0

# 確認
swapon --show
zramctl
```

`--priority 100` により、カーネルはディスクスワップより先にZRAMを使います。小さなディスクスワップはフォールバックとして残しておきますが、ほぼすべてZRAMが吸収します。

## モニタリング

```bash
# ライブ表示: DISKSIZE, DATA, COMPR, TOTAL, STREAMS, ALGORITHM
zramctl

# スワップ使用状況の要約
swapon --show

# デバイスごとのメモリ統計
cat /proc/swaps
```

`zramctl` の主要カラム:
- **DISKSIZE** — 非圧縮容量
- **DATA** — RAMに実際に保存されている圧縮後バイト数
- **COMPR** — 圧縮率（使用DISKSIZE vs DATA）
- **TOTAL** — デバイスが消費しているRAM合計

`COMPR` の値に注目してください。3x以上ならZRAMは役割を果たしています。1x付近で推移するなら、そのワークロードは圧縮に向いておらず、CPUを無駄に消費しているだけです。

## チューニング

**サイズ:** まずは物理RAMと同程度のZRAMサイズから始めます。2x〜4xに増やすのは、冗長性の非常に高いワークロードのみ意味があります。物理RAMが依然としてハードリミットです — ZRAMはメモリを創造するのではなく、既にあるものを圧縮するだけです。

**アルゴリズム:** 圧縮率重視なら `zstd`、CPUが弱くレイテンシ重視なら `lz4`。利用可能か確認:

```bash
cat /sys/block/zram0/comp_algorithm
```

**再起動後も永続化**するにはsystemdユニットか `/etc/fstab` に追加:

```fstab
/dev/zram0 none swap defaults,pri=100 0 0
```

そして `/etc/modules-load.d/zram.conf`:

```
zram
```

## 実運用での知見

- **Electron/Chromium系の重いワークロード:** プロセス間で共有ライブラリが多いため非常によく圧縮されます。32GBマシンでVS Code複数ウィンドウ＋ブラウザタブなら4x〜9xが典型的です。
- **Containerlab / Dockerラボ:** 同一ルーターイメージを多数のコンテナで動かすと、公称サイズの何分の一かに圧縮されます。48GB RAMで約100台の仮想ルーターを動かした例があります。この圧縮率はプロセスがページを共有している場合のみ成立し、異種ワークロードでははるかに低くなります。
- **大規模ビルド:** コンパイル時のメモリ確保・解放が激しく、ZRAMがディスクスワップに触れずにスパイクを吸収します。
- **過大サイズ設定は実際のリスクです。** RAMをはるかに超えるZRAM（例: 48GBマシンに128GB）は、データが実際には圧縮できない場合にCPUバウンドのスラッシングを引き起こします。見栄えのする数字ではなく、ワークロードに合わせてサイズを決めてください。
